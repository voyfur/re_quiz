# Спецификация: подбор готовых наборов в квизе Race Expert, v1

**Статус:** черновик требований для production. Принцип динамического ветвления, автоматического выбора набора backend и вспомогательной роли тегов зафиксирован; конкретные правила подбора и список допущенных наборов требуют утверждения владельцем. Отдельный локальный test-only прототип создан и не считается production-реализацией.
**Основание:** [intent.md](intent.md), [исследование выбора спортивных товаров](wiki/projects/quiz-athlete-product-selection-research.md), [техническое ТЗ по правилам подбора](wiki/projects/quiz-matching-rules-technical-brief.md) и анализ 206 наборов «За потребами».

## Постановка проблемы

Покупателю Race Expert бывает трудно выбрать товары под свою потребность. В проекте есть анкета для владельца бизнеса и отдельный локальный экспериментальный квиз; production-квиза и производственного движка рекомендаций пока нет. Каталог 206 готовых наборов «За потребами» изучен, но эта инвентаризация сама по себе не утверждает, какие наборы разрешено рекомендовать и по каким правилам.

Ожидаемые бизнес-результаты — повышение конверсии и снижение нагрузки на консультации. Базовые значения, целевые показатели и ответственный за измерение пока не определены.

## Решение

Подготовить первую версию общего покупательского квиза, в котором покупатель описывает потребность и значимые ограничения/предпочтения, а backend автоматически выбирает один или несколько утверждённых готовых наборов из категории «За потребами». Рекомендации строятся по правилам, утверждённым владельцем, и подтверждённым данным каталога. Результат содержит краткое объяснение и ссылку на страницу набора.

Логику подбора отделить от источника каталога. Для первой версии можно использовать локальный структурированный индекс; позже источник должен быть заменяемым через адаптер, чтобы подключить API сайта или базы данных без переписывания правил и контракта результата. Точная схема данных и будущий API требуют технического согласования.

## Динамический сценарий и источники сопоставления

### Подтверждённое поведение

1. **Начинать с задачи покупателя.** Вопрос выясняет цель или ситуацию обычными словами; он не просит выбрать тип набора или сам набор.
2. **Пересчитывать кандидатов после каждого ответа.** Следующий вопрос и его варианты определяются по текущему множеству совместимых наборов. Нерелевантные варианты не показываются; например, ветка силовой тренировки не должна предлагать «велоспорт», если он не соответствует выбранному сценарию.
3. **Задавать только влияющие вопросы.** Показывать вопрос, только если ответ может изменить кандидатов, обработку подтверждённого ограничения или объяснение результата. Пропускать вопросы, не меняющие выдачу.
4. **Выбирать результат на backend.** Покупатель отвечает о потребности и предпочтениях; backend возвращает готовые наборы. Ручной выбор набора внутри анкеты не является шагом подбора.
5. **Сопоставлять по нескольким источникам.** Использовать нормализованные цели/синонимы, название и описание набора, название/состав/характеристики компонентов, подтверждённые структурированные поля и теги. Теги помогают найти и ранжировать кандидатов, но совпадение только по тегу недостаточно для рекомендации.
6. **Подтверждать жёсткие условия фактами каталога.** Цена, состав, кофеин, аллергены, возрастной допуск, размер и наличие применяются как строгие ограничения только при подтверждённых данных с источником и датой проверки. Отсутствие тега не означает подтверждённое отсутствие свойства; неизвестное состояние не маскируется.
7. **Держать форму необязательной.** Не требовать выбора порошка, капсул, геля или другой формы. Предпочтение по форме можно спросить добровольно и только когда оно различает текущих кандидатов.
8. **Показывать размер только по ветке размерных товаров.** Вопрос о размере обуви/одежды появляется, только если среди текущих кандидатов есть такие товары и для них подтверждён размер. Возраст не собирать как общий профильный параметр; если у кандидатов есть явное возрастное ограничение, способ проверки возраста согласовать отдельно.

### Основание для вопросника

Исследования описывают разные приоритеты в зависимости от вида спорта и ситуации: цель/результативность, состав и безопасность, удобство и переносимость, вкус, доступность и цена. В исследовательской карточке приведены методы и ограничения источников. Найденное украинское исследование небольшое и локальное; прямых исследований выбора готовых многотоварных наборов в просмотренных источниках нет. Поэтому исследования задают гипотезы для вопросов и предпочтений, но не утверждают ранжирование наборов, эффективность продукта или правила для клиентов Race Expert.

## Истории пользователей

1. Как покупатель, я хочу ответить на короткий набор вопросов о своей потребности, чтобы быстрее выбрать подходящий готовый набор.
2. Как покупатель, я хочу пройти квиз на украинском или русском языке, чтобы пользоваться им на удобном мне языке.
3. Как покупатель, я хочу видеть только вопросы, влияющие на наборы-кандидаты, безопасность или согласованный результат, чтобы не отвечать на лишнее.
4. Как покупатель, я хочу выбирать свой бюджет, чтобы рекомендации учитывали стоимость полного набора.
5. Как покупатель, я хочу получить один или несколько подходящих наборов, чтобы сравнить варианты, если правила допускают несколько результатов.
6. Как покупатель, я хочу видеть краткое объяснение каждой рекомендации, чтобы понимать, какие мои ответы повлияли на результат.
7. Как покупатель, я хочу перейти со страницы результата на страницу выбранного набора на сайте Race Expert, чтобы узнать о нём подробнее.
8. Как покупатель, я хочу не получать неподтверждённые утверждения о составе или совместимости, чтобы не полагаться на неизвестные сведения как на подтверждённые.
9. Как покупатель, я хочу получить согласованный исход, если подходящего набора нет или данных недостаточно, чтобы квиз не выдавал случайный вариант.
10. Как владелец бизнеса, я хочу утвердить допустимые наборы и соответствие ответов наборам, чтобы квиз следовал правилам бизнеса.
11. Как владелец бизнеса, я хочу определить для каждого ответа, является ли он жёстким условием, мягким предпочтением или информационным полем, чтобы результаты имели предсказуемую логику.
12. Как владелец бизнеса, я хочу утвердить обычные примеры подбора и примеры без рекомендации, чтобы проверять ожидаемое поведение квиза.
13. Как покупатель, я хочу, чтобы границы бюджета и цена полного набора применялись однозначно, чтобы не видеть варианты вне выбранного бюджета.
14. Как покупатель, я хочу, чтобы неизвестные сведения о кофеине, аллергенах и других ограничениях не трактовались как подтверждённое отсутствие, чтобы квиз не делал необоснованных выводов.
15. Как технический специалист, я хочу видеть источник и дату проверки цены, наличия и важных характеристик набора, чтобы оценивать актуальность результата.
16. Как сопровождающий каталог, я хочу обновлять нормализованные записи наборов независимо от правил подбора, чтобы изменения каталога не требовали переписывать matching-логику.
17. Как технический специалист, я хочу заменить локальный источник адаптером к API каталога или базы данных, чтобы подключить сайт без изменения правил подбора и результата.
18. Как разработчик сайта, я хочу получать структурированный ответ backend с наборами и объяснениями, чтобы отображать результат на отдельной странице или во всплывающем окне.
19. Как владелец бизнеса, я хочу отдельно согласовать поведение для недоступных наборов, чтобы квиз не обещал товар, который нельзя купить.
20. Как владелец бизнеса, я хочу определить измеримые показатели успеха и исходные значения, если они будут критериями запуска, чтобы оценивать результат квиза по данным.
21. Как покупатель, я хочу видеть следующий вопрос и варианты, подходящие к моим предыдущим ответам, чтобы не попадать в противоречивые ветки.
22. Как покупатель, я хочу описать свою потребность, а не выбирать готовый набор, чтобы квиз сам определил подходящий результат.
23. Как покупатель, я хочу отвечать на вопрос о форме только по желанию, а о размере — только если рекомендоваться могут одежда или обувь, чтобы не отвечать на неприменимые вопросы.

## Решения по реализации

- **Объём v1:** только готовые наборы из текущей выборки 206 записей «За потребами». Сам факт наличия записи в инвентаризации не разрешает рекомендовать её: допустимые наборы утверждает владелец.
- **Отдельные сценарии:** рекомендации отдельных товаров и сборка новых наборов AI остаются за пределами v1 и требуют отдельных спецификаций.
- **Данные набора:** нормализованная запись предусматривает устойчивый внутренний `set_id`, внешний ID/SKU при наличии, название, канонический URL, утверждённые поля и теги для подбора, состав и количества при наличии, цену и дату проверки, наличие и дату проверки, источники данных и статус допуска к квизу.
- **Сменный источник каталога:** движок получает нормализованные записи через слой доступа к каталогу. Первая реализация может читать локальный JSON или другой согласованный структурированный индекс. В будущем источник можно заменить адаптером к API сайта или API базы данных. Прямое подключение к MySQL не выбрано; платформа и контракт API требуют подтверждения техническим специалистом.
- **Независимость логики:** правила сопоставления и ранжирования отделены от формата и места хранения каталога. Замена источника не должна менять правила или контракт результата.
- **Контракт результата:** backend возвращает структурированные данные о выбранных наборах и объяснениях, например JSON. Backend не возвращает заранее свёрстанный HTML. Точный состав полей — TBD.
- **Подготовка и утверждение правил:** я готовлю предложение по вопросам, вариантам ответов, условным веткам и матрице подбора на основе анализа каталога и ограничений данных. Владелец проверяет предложение, при необходимости корректирует и утверждает его. До утверждения владельцем это не основание для production. По отдельному прямому поручению может существовать изолированный test-only прототип с явно экспериментальными эвристиками; его поведение не становится правилом для сайта автоматически. См. [карточку тестовой песочницы](wiki/projects/quiz-test-sandbox.md).
- **Динамическое ветвление:** после каждого ответа backend обновляет набор кандидатов; следующие вопросы и варианты строятся по совместимым оставшимся кандидатам. Нельзя предлагать несовместимый ответ или требовать, чтобы покупатель выбрал набор. Точная карта веток и соответствия остаётся TBD до подготовки и согласования правил.
- **Источники сопоставления:** использовать совместно нормализованную цель и синонимы, текст названия/описания, состав и характеристики компонентов, подтверждённые поля и теги. Теги — вспомогательные признаки. Свободный текст может помогать находить кандидатов, но обязательные ограничения проверяются по подтверждённым структурированным данным.
- **Правила подбора:** владелец утверждает допустимые наборы, жёсткие исключения, мягкие предпочтения, ранжирование, разрешение равенств и количество результатов. До согласования матрицы эти правила остаются TBD.
- **Возможные входы:** основа — потребность и сценарий; бюджет и подтверждённые ограничения — когда они меняют кандидатов; вкус, удобство, бренд и форма — необязательные предпочтения при наличии данных. Размер задаётся только в ветке одежды/обуви. Возраст и другие дополнительные параметры используются лишь при явном ограничении у актуальных кандидатов и после согласования. Точный список, порядок и формулировки вопросов остаются TBD.
- **Семантика данных:** различать подтверждённое наличие, подтверждённое отсутствие, неизвестное и неприменимое значение. Пустое поле или отсутствие тега не означает отсутствие ингредиента, ограничения или характеристики. Поведение при неизвестных значениях согласуется отдельно для каждого правила.
- **Цена и наличие:** снимок цен от 2026-11-06 не является источником актуальной цены. Источник истины, частота обновления, допустимая давность и повторная проверка перед выдачей результата остаются TBD.
- **Бюджет:** предложенные диапазоны 500–900, 901–1500 и 1500–2500 грн пересекаются на 1500 грн. Верхняя граница и правило включения полной цены набора не определены.
- **Результат и интерфейс:** ссылка на страницу существующего набора входит в подтверждённое направление v1. Отдельная страница или pop-up не выбраны. Добавление в корзину нужно отдельно подтвердить с владельцем и техническим специалистом.
- **Безопасность:** не выводить дозировки, медицинскую эффективность, противопоказания или совместимость из маркетингового описания и пропусков в данных. Ответственный специалист и утверждённые источники пока не определены.
- **Бизнес-метрики:** повышение конверсии и снижение нагрузки на консультации являются целями, но базовые значения, целевые показатели и ответственный за измерение не заданы.

## Решения по тестированию

- Проверять внешнее поведение, а не внутреннее устройство функций или конкретный алгоритм ранжирования.
- Основная тестовая граница — backend-контракт рекомендаций: ответы покупателя и нормализованный каталог на входе, структурированный список результатов и объяснений на выходе.
- Для каждого сценария проверить, что ответы обновляют набор кандидатов, следующие варианты совместимы с выбранной веткой, а набор выбирает backend без ручного выбора покупателем.
- Проверить, что один тег не служит единственным основанием рекомендации; строгие ограничения используют подтверждённые данные, а неизвестные поля остаются неизвестными.
- Проверить условность вопросов: форма не обязательна; размер появляется только при соответствующих размерных кандидатах; вопросы без влияния на результат пропускаются.
- Использовать утверждённые владельцем примеры для совпадения, нескольких результатов, отсутствия результата, бюджетных границ и неизвестных данных. Ожидаемые результаты закреплять только после утверждения матрицы правил.
- Проверять, что замена источника каталога не меняет контракт рекомендаций; будущий адаптер к API должен предоставлять тот же нормализованный формат.
- Изолированная песочница `test-quiz-sandbox/` содержит 206 source-linked наборов, backend API подбора, локальный двуязычный интерфейс и 26 unit/handler-тестов; это test-only реализация, а не утверждённый набор production acceptance-тестов. Локальный браузерный сценарий проверен для выдачи 1/2/3 результатов, кофеина, бюджета, размера обуви, украинского языка и мобильной ширины 390 px без горизонтальной прокрутки. Корневые `index.html` и `server.py` обслуживают анкету владельца и отправку ответов в Telegram и песочницей не менялись.

## Вне объёма

- Рекомендации отдельных товаров и AI-сборка новых наборов.
- Реализация или редизайн покупательского интерфейса сайта.
- Подключение API каталога или базы данных в первой версии; для v1 используется локальный источник с возможностью позднее заменить его адаптером.
- Интеграция с корзиной до отдельного согласования её включения и технического контракта.
- Рекламные кампании, привлечение трафика и рекламная аналитика.
- Генерация медицинских рекомендаций, дозировок, инструкций по приёму или утверждений о совместимости.

## Дополнительные замечания

- Правила рекомендаций утверждает владелец бизнеса.
- Технический контакт и специалист, ответственный за проверку продуктовой безопасности, пока не определены.
- Допустимый список наборов, вопросы, матрица правил, поведение без результата, обработка неизвестных данных, актуальность цены и наличия остаются открытыми решениями.
- Инвентаризация 206 наборов подтверждает охват каталога на момент анализа, но не является разрешённым списком рекомендаций или актуальным источником остатков.
