# Локальный тестовый квиз по 206 наборам

## Статус

По запросу пользователя от 2026-11-09 созданы две локальные версии: прежний тестер по адресу `/` и покупательский HTML-прототип в стиле Windows 98 по адресу `/draft`. После обратной связи ветки стали зависеть от выбранной потребности и последующих ответов; каждый шаг показывает один вопрос. Прототип двуязычный, без графики и использует отдельную backend-логику, основанную на слоях доказательств из аудита 206 готовых наборов. **Это review-прототип: правила и формулировки не утверждены для production. Подключения к сайту ещё нет.**

По отдельному запросу пройден [аудит на 150 покупательских сценариях](quiz-buyer-scenario-audit-100.md). В алгоритм добавлены: мультивыбор предпочтений, расчёт процента соответствия (Match Confidence Score 0–99%), Near-Miss альтернативы (+100–350 ₴), Dynamic Price Hint на экране бюджета и Floor Price Anchor (минимальный базовый набор категории). Расширенный аудит на 150 сценариях показал 0 известных противоречий, 0 нарушений цены/размера и 0 истинных тупиков (100% покупателей получают персонализированные варианты или понятный стартовый комплект). В UI добавлена маркировка клубных наборов и фильтр абонементов.

Каталог `catalog.json` собран из [Wiki-анализа 206 наборов](race-expert-need-sets-206-analysis.md), содержит 206 уникальных source-linked записей и сохраняет снимок цены от 2026-11-06. Это производный локальный тестовый снимок, не источник актуальной цены или наличия.

## Запуск

Из корня проекта выполнить:

```sh
cd test-quiz-sandbox
python3 server.py
```

Для прежнего тестера открыть `http://127.0.0.1:8765/`; для покупательского квиза — `http://127.0.0.1:8765/draft`. Благодаря включению автономного клиентского бандла (`catalog_data.js` и `client_matcher.js`) страница `web/draft.html` теперь полноценно работает и автономно при прямом открытии через `file://` в браузере без запущенного сервера. Пересборка JSON из Wiki: `python3 catalog_builder.py`; пересборка клиентского бандла: `python3 build_bundle.py`. Backend отвергает привязку к нелокальному IP; ответы не записываются и обрабатываются только в памяти запроса.

## Состав прототипа

- `catalog_builder.py` — извлекает 206 записей из поддерживаемых форматов Wiki-страницы и проверяет полноту/уникальность.
- `catalog.json` — локальный нормализованный снимок для теста.
- `build_bundle.py` — генератор клиентского бандла каталога и зеркального JS-матчера.
- `matcher.py` — логика прежней формы `/`.
- `draft_matcher.py` — экспериментальный подбор для `/draft`: позиционирование продавца как основной сигнал, недиспутируемые компоненты как вторичный; расчёт процента уверенности (Match Confidence Score 0–99%), Dynamic Price Hint, Near-Miss и Floor Price Anchor.
- `server.py` — loopback-only HTTP сервер для двух форм и их отдельных API.
- `web/catalog_data.js` — сериализованный массив 206 наборов с доказательной базой для автономного офлайн-режима.
- `web/client_matcher.js` — зеркальная клиентская реализация алгоритма подбора для автономного режима в браузере.
- `web/draft.html`, `draft.css`, `draft.js` — интерфейс покупательского квиза (поддерживает работу через HTTP API и офлайн fallback через `client_matcher.js`); русский и украинский языки, тестовая пометка.
- `tests/` и `TEST_PLAN.md` — unit/handler-проверки и сценарии; test-only tickets находятся в `tickets/`.

Черновая привязка вариантов задачи к семействам из аудита: бег → `running_race_preparation`; тренировки и сила → `strength_muscle_training`; гидратация → `hydration_electrolytes`; питание и перекусы → `portable_food_snacks` и `endurance_energy`; восстановление → `recovery_fatigue` и `sleep_relaxation_stress`; походы → `outdoor_travel_hiking`; одежда → `foot_apparel_comfort`; повседневное использование → `general_daily_nutrition`; подарок → `gift_identity`. Например, общее позиционирование по энергии не превращает набор для дороги/концентрации в беговой.

Квиз `/draft` начинает с задачи и после каждого ответа пересчитывает доступные вопросы. Активность зависит от ветки: для питания доступны бег, велоспорт и походы; для тренировок и силы — силовые, функциональные тренировки, йога/пилатес и мобильность. Если нужного вида активности нет в списке, покупатель может выбрать «Другая активность»; квиз не подменяет её ближайшей категорией. В зависимости от оставшихся наборов могут появиться вопросы о классе товара, сценарии, времени и месте использования, формате старта, сезоне, форме продукта, размере обуви/носков и максимальной цене. Размер спрашивается также в подарочной ветке, если среди оставшихся кандидатов есть товар с записанным диапазоном.

Новая реализация в `draft_matcher.py` использует единое разбиение кандидатов для API вопросов и итоговой выдачи. В обычный результат попадают только наборы без известных противоречий всем выбранным ответам; точные совпадения ранжируются выше. Цена и известный размерный диапазон — жёсткие ограничения. Наборы с неизвестными сигналами доступны только по отдельному действию и помечаются как неподтверждённые; известные противоречия мягким предпочтениям доступны только по явному действию «ослабить предпочтения», с перечислением конфликтующих ответов. Известный конфликт по активности или классу товара не попадает ни в одну выдачу. Пустой пул не расширяется автоматически.

Результат с отметкой `club_membership_bundle` явно показывает, что в набор включён абонемент Race Expert Club; упоминание Club только в названии помечается как непроверенное. Это раскрывает тип набора, но не подтверждает актуальный состав. В браузере проверены общий fallback только после отдельного нажатия, ослабление мягкого предпочтения только после отдельного нажатия, питание в походе с совпадением по активности/месту, размер в подарочной ветке и видимое обозначение клубных наборов.

Точные дистанции не покрыты: точные 5 км не различаются и числовую дистанцию нельзя считать подтверждённой. Кофеин и аллергены не предлагаются как фильтры, и backend отклоняет попытку передать такие ограничения. Это пробел данных/объёма, а не повод угадывать пригодность. Цена от 2026-11-06 используется только для демонстрации; для реального бюджетного ограничения нужна актуальная цена. Старый тестер `/` сохраняет прежние входы: назначение, спорт, тип набора, форму, формат старта, цену, размер, компонент, кофеиновый фильтр и наличие; эти вопросы не относятся к новому черновику.

## Консервативная семантика данных

Следующие правила ниже описывают прежнюю форму `/`. Для `/draft` после переработки применяются отдельные правила точной, общей и явно ослабленной выдачи, описанные выше.

- Точный спорт ранжируется выше общего `not_sport_specific`; набор с другим конкретным спортом не подставляется.
- Бюджет сравнивается с полной ценой набора из снимка, цена показывается с датой.
- Размер проверяется только по записанному диапазону. Если диапазона нет, квиз сообщает об этом и не делает вывод о размере.
- В режиме «избегать кофеин» допускаются только наборы с явным `confirmed_absent`. В текущем наборе данных таких карточек нет, поэтому результат — `insufficient_data`.
- В режиме «только в наличии» остаются только записи с `availability:in_stock`; прочее состояние неизвестно.
- Возраст, вес покупателя, аллергены/лекарственные взаимодействия и числовая дистанция отвергаются backend как неподдержанные; эти вопросы не показаны в форме.
- Срок `3_months` не предлагается как вопрос покупателя: он может обозначать срок клубного абонемента, а не длительность приёма.
- Несколько наборов прямо названы альтернативами, а не совместимым комплектом.

## Проверка и ограничения окружения

Скрипт [`scenario_audit_100.py`](../../test-quiz-sandbox/scenario_audit_100.py) повторно прогнал 100 уникальных входов по текущему matcher: известных конфликтов в обычной выдаче — 0; автоматического расширения пустого пула — 0; нарушений цены и известного размера — 0. Backend отклонил 3/3 неподдерживаемых фильтра. В браузере вручную пройдены общий и ослабленный fallback, «питание → походы», «подарок → одежда → размер 42» и подпись membership-набора. Для браузерной проверки использован перезапущенный экземпляр актуального сервера; `http://127.0.0.1:8765/draft` теперь обслуживает текущий код. Снимок не подтверждает актуальность состава, цен или наличия.

Корневые `index.html` и `server.py` (анкета владельца) и анализ 206 наборов не менялись. Перед подключением backend-контракта к сайту нужно отдельно согласовать production-правила и обновить 11 конфликтных карточек; текущий прототип не использует live-цену или остатки.

## Динамический HTML-прототип покупательского квиза

- Страница: `/draft`; исходники находятся в `web/draft.html`, `web/draft.css`, `web/draft.js`. Сверка matching выполняется через `draft_matcher.py` по `wiki/projects/quiz-set-audit.json`.
- Сигналы: сначала явно заявленное продавцом позиционирование; затем товар/класс товара в недиспутируемом составе. Вторичные тексты и tag-only сигналы не формируют кандидатов. В обычной выдаче все известные противоречия выбранным ответам исключаются; неизвестные сигналы образуют отдельный общий пул, а противоречия мягким предпочтениям — отдельный пул ослабления. Ни один fallback не показывается без явного действия покупателя. Размер отсекает только при известном несовпадении диапазона; неизвестный размер не попадает в обычный точный результат.
- В демо доступен ввод максимальной цены и сравнение со снимком от 2026-11-06. На странице это раскрыто; для реального квиза цену и остаток нужно получать из актуального каталога.
- Клиентские вопросы черновика идут по одному на экран: потребность; условная активность; важный класс товара; подходящий сценарий; время и место использования отдельными предпочтениями; условные формат старта, погода и форма продукта; размер обуви/носков при наличии подтверждённого диапазона; необязательный для покупателя максимум по снимку цены. Пример веток: питание → бег/велоспорт/походы; тренировки и сила → силовые/функциональные/йога-пилатес плюс «другая активность». Размеры одежды в аудите не нормализованы, поэтому они не спрашиваются.
- Вопросы о кофеине, аллергенах, возрасте, весе, километраже, периоде курса и количестве продуктов не добавлены: источники и правила для них сейчас недостаточны либо они не помогают выбрать набор в этой версии. Форма продукта остаётся условным мягким предпочтением.
- Проверка 100 сценариев и ключевых браузерных маршрутов завершена. Следующий этап — владелец сверяет экспериментальные правила и спорные данные каталога; website/runtime-интеграция остаётся отдельной задачей. Прототип не является утверждённым production-квизом.

## Автономный скилл онбординга новых наборов (`race-expert-kit-onboarding`)

В директории `.agents/skills/race-expert-kit-onboarding/` реализован полный автономный навык агента (Antigravity Skill) для добавления новых товарных наборов по URL:
- **`SKILL.md`**: Руководство по активации и исполнению 5-фазного пайплайна (сбор сырых данных, ресерч пробелов через web search, нормализация по таксономии, инжест и аудит).
- **`references/`**: Нормативные контролируемые словари (`controlled_vocabularies.md`) и полная схема JSON (`schema_reference.md`).
- **`scripts/fetch_and_parse_kit.py`**: Парсер карточек товара с извлечением заголовка, цены, SKU, состава и генерацией задач на доисследование (`research_tasks`).
- **`scripts/normalize_kit_data.py`**: Строгий валидатор и нормализатор сигналов под 4-слойную доказательную базу движка.
- **`scripts/ingest_kit.py`**: Мастер-скрипт инжеста — назначает следующий ID, пополняет `catalog.json` и `quiz-set-audit.json`, автоматически пересобирает клиентские JS-бандлы (`catalog_data.js`, `client_matcher.js`) и автономные HTML-страницы (`public/index.html`, `quiz.html`).
- **`scripts/audit_new_kit.py`**: Скрипт проверки достижимости нового набора в целевых ветках квиза и верификации процента соответствия (Match Confidence Score).
- **Внешний сервер**: Запущен на `http://0.0.0.0:8080/` (`serve_ip.py`), отдаёт динамически обновляемый квиз с возможностью ресайза виджета во всех 8 направлениях.
